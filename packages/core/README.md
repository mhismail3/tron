# Core: proof blocks

`packages/core` holds Tron's proven decision logic as Dafny **blocks**. It has no I/O, clock or ids:
a block is pure, total and deterministic, and the shell (Gateway TypeScript) interprets its effects.
Every block is run by its shell (`block.json` names the `shell`) and is the only implementation of its logic:
the shell calls its compiled core and holds no copy of the decision.

```text
laws/<area>/<Block>.dfy          L0: abstract modules: types, signatures, law lemmas with plain-English comments
blocks/<area>/<block>/           L1: one directory per block
  Block.dfy                      `module X refines XLaws`: definitions and proofs
  block.json                     {"interface": [...], "impl": [...], "deps": [...], "shell": "<dir>"}
  mutate.json                    gate config: tier, laws map, mutated symbols, report path
  LAWS.md                        the generated law review packet (scripts/tron proof packet --write)
  MUTATION.json                  mutation report; REVIEW.json: independent law review
  method-mutants.json            a block with a compiled method: changes to it that the verifier must reject
<shell>/                         core.mjs (compiled, no Dafny runtime, no package) and facade.ts (the typed wrapper the shell imports), generated by scripts/tron
                                 proof facade into the directory block.json "shell" names; never edited
wire/Protocol.dfy                the Gateway protocol's value types (protocol v8), the one source of
                                 packages/gateway/src/protocol/types.ts (scripts/tron proof wire --protocol)
```

Blocks: `schedule/occurrence` (Automation once/interval occurrences; shell
`packages/gateway/src/automations/schedule.ts`, core in `packages/gateway/src/core/schedule/occurrence`),
`schedule/calendar` (Automation calendar occurrences over a table of the timezone's UTC offsets from
`packages/gateway/src/automations/zone-table.ts`; shell `packages/gateway/src/automations/schedule.ts`, core in
`packages/gateway/src/core/schedule/calendar`),
`settings/precedence` (which layer's value a setting resolves to, which layers are shown and what lies below a
layer, over value tokens; shell `packages/gateway/src/kernel/settings/settings-resolver.ts`, core in
`packages/gateway/src/core/settings/precedence`), `settings/tool-selection` (how a tool selection's plain
names and +name/-name modifiers compose and are stored, over name tokens; shell
`packages/gateway/src/kernel/settings/settings-types.ts`, core in
`packages/gateway/src/core/settings/tool-selection`) and `receipts/invocation-lifecycle` (how a session's
invocation receipts fold into each invocation's lifecycle, and which histories are refused; shell
`packages/gateway/src/kernel/receipts/invocation-receipts.ts`, core in
`packages/gateway/src/core/receipts/invocation-lifecycle`).

## Block contract

- `block.json` lists the block's `interface` (its laws files), its `impl` (definition and proof files),
  both relative to `packages/core`, its `deps` (other block names; a block's name is its directory
  under `blocks/`, e.g. `schedule/next`) and the `shell`'s directory relative to the repository.
- A block compiles without the Dafny runtime, so the shell needs no package for it and its
  arithmetic is JavaScript's own. Its compiled code may use only bounded newtypes (a literal integer range within
  the JavaScript safe integers; the proof shows no value leaves it), booleans, datatypes (constructors, `.C?`
  tests, fields, updates), reads of sequences and arrays, and loops; integer `/` and `%` use the compiler's own
  helper. An unbounded `int`, building a sequence, datatype `==` and tuples need the runtime and are refused when
  the core is generated; ghost code is not compiled and may use anything. A block that builds a list builds a
  linked list (`datatype List<T> = Nil | Cons(head: T, tail: List<T>)`) with tail-recursive functions, which
  compile to loops; the façade passes it to and from the shell as an array. Its laws may define what it computes
  over sequences in ghost functions and state that the compiled functions compute exactly that
  (`settings/tool-selection`). A fold that needs a table works in arrays: a compiled method whose arrays the façade
  lends (it cannot allocate one without the runtime), whose contract is the law that it computes the fold as
  defined, and whose pure decisions are functions the mutation check covers (`receipts/invocation-lifecycle`).
  Types that exist for the laws only have ghost constructors, so nothing is compiled for them.
- A dependent sees only its deps' laws: it imports their abstract modules. A block's impl files include
  only its own files and its transitive deps' interface files; its interface (laws) files include only
  interface files, since dependents follow them. `proof check` refuses any other include (also one
  behind a comment), because the cache key would not cover what the block depends on.
- Law statements are what review guards; definitions and proofs are what the checker guards. Edit a
  law only with an independent review of that law.
- The mutation tool mutates functions and predicates, never a method: a method's loops carry proof annotations it
  cannot tell from code. A compiled method is listed in `excludeSymbols`, its contract says exactly what it
  returns, every decision in it that could be a function is one, and the block's `method-mutants.json` lists
  hand-made changes to its statements (`[{from, to}]`), each of which the gate test shows the verifier rejects.
- Escape hatches (`assume`, `{:axiom}`, `{:verify false}`, `{:extern}`) are trusted code and need a
  maintainer decision.

## Gates

Before a block can gate anything, all of these hold at its current block hash (tools/proof/README.md):
proof check PASS; `proof mutate` PASS (every mutant killed by a law or proven equivalent); an independent
reviewer (a different agent and, for high-stakes, a different model from the writer) ACCEPTs every law;
and `LAWS.md` is regenerated. `tools/proof/tests/test-core.py`
enforces this on every change here and on every change to a generated core. The shell's own test pins what its
callers see around the block (for the schedule blocks, `packages/gateway/src/automations/schedule.test.ts`).

## Check

```bash
scripts/tron proof check                 # every block, plus everything below it
scripts/tron proof check schedule/next   # one block and the blocks below it
```

The check uses only the pinned toolchain (`scripts/tron proof doctor` must pass; see
[tools/proof](../../tools/proof/README.md)) with one solver process. A block's key covers the pin, the
checker, its own files and the laws of every block below it, so a proof edit re-checks one block and a
law edit re-checks every block above it. Passing keys are cached per worktree.
